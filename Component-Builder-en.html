Establish a fair comparison

Pin the Figma node and version. Run the Paparazzi screenshot test on the current code and check the state, viewport, dimensions, and source revision. For an existing visual change, also compare the before and current renders.

Inspect the images and describe the defect

Run visual-compare in embedded mode to produce a three-panel comparison.png per state. The implementer records visual observations separately from pixel metrics. Missing inputs or unavailable image inspection block validation.

Visual correction loop

How does it know a fix worked?

01

Trace the discrepancy to the code

The implementer assigns an issue ID and starts with the highest-impact discrepancy. It checks that the captures are comparable, then traces the design property to the code, such as end padding applied twice.

02

Fix the cause and capture again

On the target branch, it makes a focused fix. With the design version and rendering conditions fixed, it reruns Paparazzi and visual-compare, saving each pass with its revision and uncommitted changes.

03

Recheck the same ID and decide what follows

It records both measurements, inspects the new images and sibling states, and reruns affected checks. The issue closes when its criterion is met. Two stalled passes or missing inputs trigger a request for human judgment.

Commit & open the PR

Prepare the PR for its evidence.

01

Check the staged files, then push

In an authorized full workflow, the agent checks the staged files, commits the component and tests, and pushes the working branch. Figma exports and comparison reports stay outside the source tree.

02

Fill in the PR template

It documents scope, compatibility, test commands, and outcomes. The Visual validation section lists the states, Figma nodes and version, capture sources, observed differences, and their disposition.

03

Record what is still pending

The recorded branch is the default base. For a named existing PR, the agent uses its actual head branch. Images are marked unpublished until attached. Blocked validation or review keeps the PR in draft.

Browser upload & verification

Attach screenshots in the PR itself.

01

Open the approved Enterprise PR

After creating the PR, the agent calls its built-in browser tools, opens the target PR, and edits its description. This repository’s GitHub Enterprise Server does not support gh pr edit --attach.

02

Attach each state’s comparison.png

In the Visual validation section, it uses the web attachment control to add each state’s three-panel image. It waits for the upload to finish, then saves, preserving existing text and image proportions.

03

Reopen the description and verify each image

It checks loading, aspect ratio, and decoded pixels against the intended file. If the browser is unavailable, it can ask for a manual upload. Upload or verification failures and reviewer-access limitations are reported explicitly.

PR handoff & independent review

A second agent reviews the PR.

01

Give the reviewer the exact revision

Once evidence or blockers are documented, a separate agent runs pr-review on the PR URL, base and head refs, and exact head SHA.

02

Validate and publish the review

The reviewer reads the code, prepares comments, and checks them against the live PR. In the authorized full workflow it posts the review, including a summary when there are no findings.

03

Keep outstanding decisions explicit

The handoff links the PR, evidence, and review outcome. Blocked validation or open visual defects keep the PR in draft. Design sign-off and permission to record screenshot baselines are separate decisions.
